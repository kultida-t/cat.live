# แผนพัฒนาแมว.live ตามมาตรฐาน UNIVERZA (Dev Roadmap)

> **สถานะ:** ร่างวิเคราะห์ — รอพี่มาเต็ม/พี่คิงตรวจ ยังไม่ใช่ baseline
> **อิงจาก:** มาตรฐาน UNIVERZA ที่พี่คิงแจ้งในกลุ่ม (3 ภาพ: 7-Layer App Standard, Future App Concept & Defensible Platform, UOAA Reference Architecture) + `docs/requirement-analysis.md` + `docs/design-spec.md`
> **จัดทำเมื่อ:** 2026-11-10

---

## 1. กติกาจากพี่คิงที่ทุกโปรเจกต์ต้องยึด

1. ภาพ **UOAA Reference Architecture** และ **Future App Concept** = Standard Requirement ตอนเริ่มทำโปรเจกต์ทุกตัว
2. ชั้น 2 **Embedded AI** (AI Chat, Voice, Analysis) → ต้องมีในทุกแอป
3. ชั้น 3 **Agent Interface** (API, MCP, Webhook) → ให้ "แตะไว้เลย" ตั้งแต่ต้น สุดท้ายทุกแอปต้องมีเช่นกัน

## 2. มาตรฐาน 7 ชั้น เทียบกับแมว.live

| # | ชั้นมาตรฐาน | ในแมว.live คืออะไร | สถานะตอนนี้ |
|---|---|---|---|
| 1 | Human Interface | แอปมือถือ React Native (Expo) ตาม `design-spec.md`, เว็บ prototype เป็น design reference | มี prototype แล้ว — ต้องเขียนแอปจริง |
| 2 | Embedded AI *(บังคับทุกแอป)* | Cat AI: แชทถามอาการ, พิมพ์+เสียง, โทรคุยสัตวแพทย์ AI, ตรวจใบหน้าแมว (face-check) | มี UX แล้ว — ต้องทำจริงผ่าน AI Model Router |
| 3 | Agent Interface *(แตะไว้ตั้งแต่ต้น)* | REST API แบบ OpenAPI ตั้งแต่วันแรก + เผื่อ MCP server + Webhook (เบาะแส, แมวหาย, แจ้งเตือน) | ต้องใส่ในการออกแบบ Phase 0 |
| 4 | Business Engine | กฎธุรกิจกลาง: ประกาศ 5 แบบ↔ฟีด, โหมดแมวหาย, ระดมทุน, workflow ปิดประกาศ/อนุมัติ | กระจายอยู่ใน requirement — ต้องรวมเป็นชั้นบริการกลาง |
| 5 | Data Intelligence | PostgreSQL + PostGIS (พิกัด/แผนที่) + pgvector (ความรู้ให้ Cat AI) + search | ต้องวาง schema ตั้งแต่ Phase 0 |
| 6 | Integration Engine | LINE OA/LINE Login, Google Maps, ชำระเงิน QR, SIP/เสียง (AI call), แชร์ต่อแอปอื่น | เฟสหลัง — เผื่อจุดต่อไว้ก่อน |
| 7 | Trust & Governance | ยืนยันตัวตน, PDPA/consent, กฎ "ฟิลด์ลับห้ามออก API สาธารณะ" รายฟิลด์, audit log, ระบบรายงาน | **หัวใจของแอปนี้** — ต้องเริ่มตั้งแต่ schema แรก ห้ามทำย้อนหลัง |

## 3. มาตรฐาน U-01 ถึง U-12 ที่เกี่ยวกับแมว.live

| รหัส | มาตรฐาน | แปลงเป็นงานของเรา |
|---|---|---|
| U-01 | Responsive Human UI | มาตรฐานบังคับแค่ "UI ต้อง responsive" ทุกขนาดจอ — ส่วนฐานออกแบบ 390×844 (iPhone 14) เป็นตัวเลือกของเราเองจาก `design-spec.md` ไม่ใช่ตัวเลขที่ UOAA กำหนด |
| U-02 | AI Assistant | Cat AI เป็นผู้ช่วยหลักของแอป |
| U-03 | API First | ทุกบริการเปิดผ่าน OpenAPI spec ก่อนเขียนจอ |
| U-04 | MCP Ready | วางโครง MCP server ตั้งแต่ต้น (tools: ค้นแมวหาย, สถานที่, สร้างประกาศ) |
| U-05 | Unified Identity | OIDC/OAuth ออกแบบให้ย้ายขึ้น UNIVERZA Gateway ได้ + LINE Login |
| U-06 | Permission | สิทธิ์รายฟิลด์: ที่อยู่/บัญชี/จุดสังเกต เห็นเฉพาะเจ้าของ |
| U-07 | Data Ownership | ผู้ใช้ลบ/ส่งออกข้อมูลตัวเองได้ตาม PDPA |
| U-08 | Event Driven | เหตุการณ์กลาง: แมวหาย, เบาะแสใหม่, แจ้งเตือน, ชำระเงิน |
| U-09 | Integration | LINE OA, payment QR, Google Maps, แชร์ต่อ |
| U-10 | Auditability | audit log ทุก action สำคัญ (ประกาศ, เบาะแส, เงิน, สิทธิ์) |
| U-11 | AI Independence | AI Model Router กลาง — เปลี่ยน provider ได้โดยไม่แก้แอป |
| U-12 | Security & Recovery | สำรองข้อมูล, นโยบายกู้คืน, rate limit, ลบ EXIF GPS ก่อนเก็บรูป |

## 4. Tech Stack ที่ตกลงใช้วางแผน

| ส่วน | เทค | หมายเหตุ |
|---|---|---|
| แอปมือถือ | React Native + Expo | ตาม `design-spec.md` |
| Backend | Node.js + NestJS (TypeScript) | ภาษาเดียวกันทั้งสแตก โมดูลแบ่งตามโดเมนตรงชั้น Domain Services ของ UOAA |
| API | REST + OpenAPI spec | ตรง U-03 API First |
| ฐานข้อมูล | PostgreSQL + PostGIS + pgvector | ตัวเดียวครอบ: ข้อมูลหลัก / พิกัดแผนที่ / ความรู้ AI |
| เครื่องมือดู DB | pgAdmin 4 | เครื่องมือบนเครื่อง dev (อยู่ใน `env-setup.md` ข้อลงเครื่องแล้ว ไม่ใช่ส่วนของระบบ) |
| Cache/คิว | Redis | cache, rate limit, คิวงานพื้นหลัง (ลบ EXIF, แจ้งเตือน) |
| ไฟล์สื่อ | CloudImageLab (บริการกลางของบริษัท) | อัปโหลด+resize รูป/วิดีโอผ่าน API เดิมของทีม ไม่ทำเอง |
| เอกสารกลาง | UGC (Univerza Governance Center) | เอกสารที่ล็อก baseline/PDPA ย้ายขึ้น UGC ตามประกาศ — ร่างอยู่ใน git ได้จนกว่าล็อก |
| ข้อมูลภายนอก | Today (บริการกลาง) — optional | widget อากาศ/ฝุ่น เฟสหลังถ้าต้องการ |
| ยืนยันตัวตน | OIDC + LINE Login | ออกแบบให้ย้ายขึ้น UNIVERZA Gateway ได้ (U-05) |
| AI | AI Model Router กลาง + เผื่อ MCP server | ตรงข้อ 2-3 ของกติกาพี่คิง |

## 6. ประเด็นค้างที่ต้องถามพี่คิง/BA

**ข้อ 1 — แอปยืนตัวเองก่อน หรือต่อเข้า UNIVERZA Gateway ตั้งแต่แรก?**
- **ถามเรื่องอะไร:** UNIVERZA Gateway คือ "ด่านหน้ากลาง" ที่ทุกแอปในตระกูล UNIVERZA ใช้ร่วมกัน — ระบบล็อกอิน เช็กสิทธิ์ จำกัดจำนวนคำขอ จะผ่านตัวกลางนี้ คำถามคือแมว.live จะทำระบบล็อกอิน/สิทธิ์ของตัวเองไปก่อน แล้วค่อยย้ายขึ้นตัวกลางตอนพร้อม หรือต้องต่อเข้าตัวกลางตั้งแต่วันแรกเลย
- **ทำไมต้องถาม:** ถ้าต่อตัวกลางตั้งแต่แรกจะตรงมาตรฐานที่สุด แต่ต้องพึ่งระบบของทีมกลาง (เริ่มช้าลง ติดตามความพร้อมเขา) ถ้ายืนตัวเองก่อนจะเริ่มเร็ว แต่ต้องออกแบบเผื่อย้ายไว้ตั้งแต่ต้น ไม่งั้นตอนย้ายจะเจ็บ
- **ตอบได้แบบไหน:** (ก) ยืนตัวเองก่อน ออกแบบเผื่อย้าย หรือ (ข) ต่อ Gateway ตั้งแต่แรก

**ข้อ 2 — "แตะ" Agent Interface แค่ไหนถึงเรียกว่าถึงเกณฑ์?**
- **ถามเรื่องอะไร:** Agent Interface คือช่องทางให้ AI agent หรือระบบอื่นมาเรียกใช้แอปเราได้ เช่น AI ตัวอื่นสั่ง "ค้นหาประกาศแมวหายย่านนี้" แล้วแอปตอบข้อมูลกลับไป พี่คิงสั่งให้ "แตะไว้เลย" ตั้งแต่ต้น — คำถามคือคำว่า "แตะ" หมายถึงระดับไหน
- **ทำไมต้องถาม:** ถ้าแค่เขียน API ปกติ + วางโครง MCP (ช่องต่อสำหรับ AI) เปล่า ๆ ไว้โดยยังใช้จริงไม่ได้ งานจะเบา แต่ถ้าต้องมีคำสั่งที่ AI เรียกใช้ได้จริงตั้งแต่แรก (เช่น อ่านข้อมูลสถานที่/ประกาศแบบอ่านอย่างเดียว) งานจะหนักขึ้นและต้องจัดเฟสใหม่
- **ตอบได้แบบไหน:** ในเวอร์ชันแรกต้องมีถึงระดับไหน — (ก) เตรียมโครงไว้เฉย ๆ (ข) มีคำสั่งอ่านข้อมูลใช้ได้จริงบางส่วน (ค) เปิดครบทั้งอ่านและเขียน

**ข้อ 3 — Embedded AI ต้องอยู่ในเวอร์ชันเปิดตัวแรกไหม?**
- **ถามเรื่องอะไร:** มาตรฐานบังคับว่าทุกแอปต้องมี AI ในตัว แต่ไม่ได้บอกว่าต้องมีตั้งแต่วันเปิดตัวเลยหรือตามมาทีหลังได้ — ในแผนนี้หนูวาง Cat AI ไว้เฟส 5 (หลังระบบหลักนิ่ง)
- **ทำไมต้องถาม:** ถ้าบังคับว่าเวอร์ชันแรกต้องมี Cat AI ใช้ได้จริง ต้องดึงเฟส 5 ขึ้นมาก่อนเฟส 3–4 ทำให้ลำดับงานเปลี่ยนและเวลาเปิดตัวอาจยาวขึ้น
- **ตอบได้แบบไหน:** (ก) ต้องมีในเวอร์ชันเปิดตัวแรก หรือ (ข) เปิดแอปก่อนแล้ว Cat AI ตามมาเวอร์ชันถัดไปได้

**ข้อ 4 — เอาแผนนี้ไปคุยกับ BA ต่อเลย หรือรอคำตอบ 35 ข้อก่อน?**
- **ถามเรื่องอะไร:** เอกสารวิเคราะห์ requirement ของเราทั้งก้อนยังเป็น "ร่าง" รอ BA ตอบคำถาม 35 ข้อใน `docs/questions-for-ba.md` — ถ้าคำตอบทำให้ฟีเจอร์เปลี่ยนใหญ่ (ตัดออก/เพิ่มเข้า) ลำดับเฟสในเอกสารนี้ก็อาจต้องจัดใหม่
- **ทำไมต้องถาม:** จะได้รู้ว่าแผนนี้ถือเป็น "กรอบคุยต่อ" ได้เลย หรือควรรอ requirement ล็อกก่อนค่อยถือเป็นของจริง
- **ตอบได้แบบไหน:** (ก) ใช้แผนนี้เป็นกรอบคุยต่อได้เลย ปรับอีกทีเมื่อ BA ตอบครบ หรือ (ข) รอคำตอบ BA ก่อนค่อยล็อกลำดับเฟส

**ข้อ 5 — แมว.live หาเงินแบบไหนเป็นหลัก?**
- **ถามเรื่องอะไร:** ใน UOAA มีตาราง Revenue Model ให้เลือกหลายแบบ เช่น สมาชิกรายเดือน, เก็บ % ต่อธุรกรรม, คิดตามจำนวนผู้ใช้, ค่าเปิด API ฯลฯ — แมว.live มีช่องทางเงินอยู่แล้วคือ เลี้ยงขนม / บริจาค / ระดมทุน / ขาย Tag
- **ทำไมต้องถาม:** รูปแบบรายได้เปลี่ยนวิธีออกแบบระบบเงิน เช่น ถ้าเก็บ % จากการเลี้ยงขนมต้องมีระบบหักส่วนแบ่งอัตโนมัติ ถ้ามีสมาชิกรายเดือนต้องมีระบบต่ออายุ/ยกเลิก — ออกแบบผิดแบบตั้งแต่ต้นทีหลังแก้ยาก
- **ตอบได้แบบไหน:** เลือกรูปแบบหลัก เช่น (ก) เก็บ % จากการเลี้ยงขนม/บริจาค (ข) แพ็กเกจสมาชิก (ค) ผสมหลายแบบ — หรือบอกว่ายังไม่ตัดสินใจ ให้ทำแค่รับ-จ่ายธรรมดาก่อน
